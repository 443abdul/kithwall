# Kithwall 2: message franking (verified reports)

Status: implemented · 2026-11-02 · roadmap item 10 (`roadmap-2026-11.md`) · see also `03-safety.md`
(reporting) and `06-security-review.md` (D4, report forgery)

When someone reports an abusive chat message, they can include the message together with cryptographic
proof that the sender really sent it, in that chat, at that time. A reporter can't forge such a report, a
sender can't deny it, and the server still can't read any message nobody reports.

Code: `packages/crypto/src/franking.ts` (primitives), `apps/web/src/lib/chat/franking.ts` (chat helpers),
`lib/messages.ts` (`sendMessage`, `editMessage`, `readMessage`), `lib/safety/checkins.ts`,
`components/messages/MessageActions.tsx` (report dialog), `components/mod/verify.ts` and `ModScreen.tsx`
(moderators), `lib/media.ts` (file digests), migration `20261102000600_message_franking.sql`.

## 1. Why, given that messages are already signed

Every message envelope is signed with the sender's Ed25519 identity key (`envelope.ts`), and reports already
disclosed the message's own content key so moderators could check the signature against the server's copy
of the ciphertext. That works only while the ciphertext still exists. Kithwall deletes it on purpose:
disappearing messages (on by default), unsend, edits (no history), moderator removal. A sender who unsent a
threat before the report was reviewed left nothing to check. Franking closes that gap, lets the server check
the evidence at the moment the report is filed (not only in a moderator's browser), and gives recipients a
check of their own.

Deniability is unchanged by this work: messages were already signed, so they were already attributable to
anyone holding the decrypted envelope.

## 2. Scheme

After Facebook's Messenger Secret Conversations ("Messenger Secret Conversations", Technical Whitepaper,
2017) and Grubbs, Lu & Ristenpart, *Message Franking via Committing Authenticated Encryption* (CRYPTO 2017),
with the attachment lesson of Dodis, Grubbs, Ristenpart & Woodage, *Fast Message Franking: From Invisible
Salamanders to Encryptment* (CRYPTO 2018).

| Value | Definition |
|---|---|
| `fk` | 32 random bytes, fresh for every message and every edit; sealed INSIDE the encrypted payload (`payload.fk`) |
| `body` | `canonicalJson({ v: 1, conv, id, sender, payload })`, where `payload` is the message payload without `fk` |
| `commit` | `HMAC-SHA-256(fk, "kithwall/v1/frank\n" ‖ utf8(body))`, base64url; stored in `messages.frank_commit`, outside the ciphertext |
| `K_s` | 32 random bytes in `kw_secret.franking_keys`, generated by the migration inside the database |
| `tag` | `HMAC-SHA-256(K_s, "kithwall/v1/frank-tag\n" ‖ conv ‖ "\n" ‖ id ‖ "\n" ‖ sender ‖ "\n" ‖ µs(time) ‖ "\n" ‖ commit)`; `messages.frank_tag` |

1. **Send** (`sendMessage`): the device picks `fk`, computes `commit` over the payload it is about to seal,
   seals `{…payload, fk}` as usual (padding unchanged: `fk` is inside the padded plaintext) and inserts the
   row with `frank_commit`.
2. **Tag** (`kw.messages_frank`, trigger `messages_seal_frank`, runs after `messages_guard`): the database
   replaces any client-supplied tag with `tag`, binding the commitment to the sender, the conversation, the
   message id and its own clock (`created_at`, or `edited_at` for an edit). The function that computes tags is
   not callable by users.
3. **Receive** (`readMessage`): after the signature check and decryption, the device recomputes `commit`
   from what it decrypted. A mismatch, or a commitment with no `fk` in the payload, renders the message as
   *"This message couldn't be verified."*: it is never shown as genuine. A message with no commitment at all
   (older app, server notice) is shown normally.
4. **Report** (`MessageActions`): "Include the message" (on by default, explained in the dialog). With it on,
   the device sends `{fk, body, commit, tag, conv, sender, at}` in `reports.disclosed.frank` (plus the content
   key, so a moderator can still check the stored envelope's signature while it exists). With it off, nothing
   from the message is sent. The dialog says whether the message carries proof.
5. **Verify** (`kw.report_frank`, called by `kw.reports_guard` on insert): checks `commit` (HMAC under `fk`),
   the binding (the stored row if it still holds this commitment, else the tag over the claimed
   conversation, sender and time against every key in `kw_secret.franking_keys`), and that `body` names the
   reported message id, that conversation and that sender. The verdict goes into `reports.frank`, which the
   reporter can't pre-fill and nobody can change afterwards: `verified` (with sender, chat, time), `failed`
   (with a reason), `none` (message included without evidence) or `not_included`.
6. **Moderate** (`/mod`): a "Sender proof" fact (Verified / Didn't check out / Couldn't be verified / Message
   not included). For a verified report the committed body is the content shown; the moderator's browser
   also checks that the body is canonical JSON.

**Verified evidence is enough to file a report**, even when the message has since been unsent or deleted, or
the reporter was removed from the chat: the tag proves the sender sent exactly this into that chat, and
holding `fk` with the plaintext proves the reporter's device (or someone they gave it to) received it.
Without verified evidence the old rule stands ("cannot report what you cannot see").

## 3. Coverage and decisions

| Kind | Franked | Notes |
|---|---|---|
| Text, link previews, replies, story replies | yes | the whole payload is committed |
| Photos, videos, voice notes, link images | yes | through their `FileRef`s, which include the file key and `sha` (SHA-256 of the stored ciphertext, `fileDigest`). Without the digest a sender could delete and re-upload different content under the same path and key after sending. Downloads check `sha` when present (`lib/media.ts`). |
| Group chats, circle chats | yes | same path; `conv` is in the body and the tag |
| Edits | yes, separately | each edit gets a fresh `fk` and commitment, tagged with the edit time. The server drops the old commitment on any edit that doesn't bring a new one. A report made with evidence saved before the edit still verifies through its tag. |
| Unsend | wiped | the tombstone keeps no commitment. Evidence the reporter already has still verifies through its tag. |
| Disappearing messages | yes | after deletion, evidence verifies through its tag |
| Safety check-in alerts | yes | the commitment is made when the alert is sealed (`safety_checkin_alerts.frank_commit`) and tagged when it is released |
| System events (added, renamed, left) | yes | they are ordinary sealed messages |
| Server notices (timer, call, roster) | no | no content; written by the server |
| Reactions | no | an emoji from a fixed set of six, sealed separately (`lib/chat/reactions.ts`); report the person or the message instead |

**Downgrade.** A modified or old app can send messages without a commitment. Those display normally, and a
report of one is marked *couldn't be verified* once the stored envelope is gone (while it exists, the
signature check still applies). `app_settings.franking_required` (Moderation → Admin, off by default) makes
the database refuse new messages, edits and check-in alerts without a commitment; turn it on once every
supported app sends them. Check-in alerts armed before it was switched on are still released.

## 4. Threat model

- **The server learns nothing new about unreported messages.** `commit` is an HMAC under a random 32-byte key
  the server never sees, so it is a pseudorandom value that can't be linked to the content or to other
  messages (a fresh `fk` per message and edit). `tag` is computed from values the server already holds plus
  `commit`. The data map classifies both columns as `hashed`.
- **A reporter can't forge a report.** Making a `body` that verifies needs a `commit` the server tagged for
  that sender, chat and time, plus an `fk` and body that open it: a second preimage for HMAC-SHA-256. A
  reporter can't move real evidence to another sender or chat (the tag binds them and the body repeats them)
  or to another message id.
- **A sender can't deny a verified report.** The commitment is checked by every recipient on arrival, so
  content that displays as genuine is content the commitment binds; the server's tag binds who sent it into
  which chat and when, from the server's own view of the insert.
- **Invisible salamanders.** The AEAD underneath (XChaCha20-Poly1305) is not key-committing, but nothing here
  relies on that: the commitment is over the plaintext the recipient saw, and attachments are bound by file
  key plus ciphertext digest, so a ciphertext that decrypts differently under two keys can't make a report
  show something other than what the reporter's device displayed.
- **What a report reveals.** Exactly the included message (text, file references with their keys, voice
  metadata), `fk`, and who sent it, when, in which chat. Not other messages, not the chat key (only that
  message's own content key), not the reporter's identity to the sender.
- **Limits.**
  - Whoever holds `K_s` (the database, its backups, an operator or an attacker with full database access) can
    mint tags and so fabricate "verified" reports. This is inherent to server-side franking (Facebook's
    design has the same property). The key never leaves the database, isn't readable through the API, and
    isn't held anywhere else. It doesn't help anyone read messages.
  - A malicious server can alter a commitment (recipients then see "couldn't be verified": a visible denial of
    service, not a forgery) or strip it (the message then shows as unfranked, and a report of it is "couldn't
    be verified"). It can't make a tampered message look verified.
  - Evidence lives only on the reporter's device while the message is on screen; Kithwall keeps no plaintext
    copy of received messages for later reporting (that would defeat disappearing messages). In practice
    this protects reports filed while the sender unsends, and reports of the version before an edit only if
    the reporter's app still had it.
  - Moderators don't see media in `/mod` (unchanged); the file references and digests prove which files
    were sent.
  - Franking proves who sent a message, not that it is abusive, and not what the sender's device displayed
    to them.

## 5. Key rotation

New tags use the newest row in `kw_secret.franking_keys`; verification accepts any row. To rotate, insert
`extensions.gen_random_bytes(32)` as a new row (as `postgres`). Delete an old key only when no report could
still need it.

## 6. Tests

- `packages/crypto/test/franking.test.ts`: an independent HMAC-SHA-256 vector (shared with the SQL test),
  binding of text, attachments, chat, id and sender, canonical bodies, unlinkable commitments, malformed input.
- `apps/web/src/lib/chat/franking.test.ts`: send → verify round trip, tampering is `bad`, no commitment is
  `none`, edits get fresh keys, report evidence matches what the server checks.
- `supabase/tests/franking.test.sql`: the key is unreadable and the tag functions uncallable by users, tags
  replace client values, malformed/non-canonical commitments are refused, `franking_required`, verified /
  failed (wrong key, doctored body, wrong sender, re-attributed or forged tag) / none / not_included reports,
  immutable verdicts, edits re-tag or drop, reports after edit, unsend, deletion and removal from the chat,
  check-in alerts tagged on release.
